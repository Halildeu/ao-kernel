# v4.x Governed Control-Plane Release Checklist

**Status:** release-planning checklist / not release authority
**Date:** 2026-06-25
**Scope:** next safe governed-control-plane minor release only

This checklist is the operator-facing preparation surface for a future v4.x
minor release that ships governed-control-plane hardening and consumer
onboarding improvements. It is not a v5.0.0 release plan, not a production
platform claim, and not authority to publish a tag.

## Non-Authority Boundary

This document does not authorize:

- support widening;
- production platform claims;
- live adapter execution;
- v5.0.0 release, tag, or publish;
- bypassing `ao-release-gate`;
- replacing provider-distinct review evidence with a same-provider or synthetic
  review.

Release authority remains the repo-owned `ao-release-gate` required check plus
GitHub branch protection. AI output is review evidence only.

The historical v5.0.0 general-purpose production-promotion route is superseded

`support_widening`, `production_platform_claim`, or `live_adapter_execution`
changed unless a future operator-bound PR explicitly changes those boundaries.

## Required Preflight Before Tag

Before an operator tags a v4.x release, collect and record:

1. `python3 scripts/gpp_next.py` output showing GPP closed, no blocked work
   packages, and all three guard flags false.
2. CI status for the release candidate commit:
   - lint;
   - typecheck;
   - Python 3.11/3.12/3.13 tests;
   - coverage;
   - packaging smoke;
   - CodeQL;
   - Trivy;
   - `ao-release-gate`;
   - `ao-release-gate-review`;
   - `ao-release-gate-technical`.
3. `python3 scripts/repo_intelligence_tier_promotion_readiness.py --output json
   --evidence-manifest .claude/plans/RI-7-EVIDENCE-MANIFEST.v1.json` output
   remains `ready_for_operator_promotion_decision` with guard flags false.
4. `CHANGELOG.md` has a release entry that frames the release as governed
   control-plane hardening, not production platform promotion.
5. `pyproject.toml` version and any release notes agree on the same v4.x
   version.
6. `docs/V5-GOVERNED-CONTROL-PLANE-READINESS-GAP.md` still says v5.0.0
   tag/publish is not open now.
7. Any open high-risk governance PRs are either green through `ao-release-gate`
   or explicitly excluded from the release candidate.

## High-Risk Gate Prerequisite

Issue `#985` / PR `#997` is a high-risk governance hardening path. Its current
acceptable state is fail-closed until real MiniMax review evidence exists:

- normal CI may pass;
- a `BLOCK` MiniMax evidence file is not release approval;
- the fix must not be merged by weakening the provider quorum;
- no synthetic MiniMax `AGREE` may be used;
- a real MiniMax provider review must be bound to the exact PR changed files
  before `ao-release-gate` can pass.

If #997 remains red, a v4.x release may still proceed only if the release
candidate explicitly excludes that branch and the release notes do not claim
the high-risk provider-separation hardening as shipped.

## Release Engineering Best Practices

Use these as checklist requirements, not marketing claims:

| Practice | Required v4.x handling |
|---|---|
| SemVer | Minor version for governed-control-plane hardening; no major v5 signal. |
| PyPI trusted publishing | Use the existing OIDC `publish.yml` workflow from a `v*` tag. |
| Distribution validation | Keep `twine check dist/*.whl dist/*.tar.gz` and packaging smoke green. |
| Security evidence | Record CodeQL, Trivy, and secret scan status for the candidate commit. |
| SBOM/license discipline | Include current SBOM/license artifacts if generated by CI; do not claim final v5 release-bound evidence. |
| Provenance | Record commit SHA, tag, workflow run URL, artifact digest, and PyPI project version. |
| Rollback | Document tag/publish rollback or yanked-release path before announcement. |
| Release notes | State explicit non-authority: no support widening, no production platform claim, no live adapter execution. |

These controls align with common mature open-source release practice: trusted
publishing rather than long-lived PyPI tokens, source-pinned required checks,
machine-readable release evidence, explicit rollback notes, and conservative
claim language. They intentionally do not copy framework-specific marketing
from adjacent AI orchestration projects; ao-kernel's differentiator is governed
release evidence and fail-closed authority boundaries.

## v5.0.0 No-Go Rule

A v5.0.0 tag or publish is blocked unless a future operator-bound supersession
explicitly changes the release target and passes `ao-release-gate`. The
autonomous lane must stop if a proposed release would:

- change any guard flag from `false`;
- claim general-purpose production-platform readiness;
- rely on local/operator credentials as public production evidence;
- bypass a red `ao-release-gate`;
- treat Claude, Codex, MiniMax, or any other model output as release authority;
- publish a major version solely because the readiness manifest is prepared.

## Operator Tag/Publish Runbook Sketch

When an operator chooses to release a v4.x candidate:

1. Confirm the target commit is `origin/main` and CI is green.
2. Confirm this checklist's no-go conditions are absent.
3. Update version and changelog in a normal PR if needed.
4. Let `ao-release-gate` and branch protection merge the PR.
5. Create a `v4.x.y` tag from the merged commit.
6. Let `.github/workflows/publish.yml` publish through PyPI trusted publishing.
7. Verify `pip install ao-kernel==<version>` in a clean environment.
8. Record the tag, workflow run, PyPI URL, artifact digest, and post-publish
   smoke result in a release evidence note.

This sketch is intentionally not an instruction to tag now.
